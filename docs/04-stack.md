# 暂定技术选型

核对日期：2026-09-05。以下基础栈适用于高亮输入、四路辅助和整书地图；2D、PDF、本机单人演示仍是建议。D06/D09/D05 的实现深度、检索范围和路由策略确认后再锁定服务。官方能力说明不等于已经验证本项目集成、延迟或账号访问权限。

## 一套默认组合

| 层 | 建议 | 理由及边界 |
| --- | --- | --- |
| 网页与服务端 | TypeScript + React + Next.js App Router | 一个项目容纳界面与模型代理；Route Handlers 支持请求处理，避免另建服务。[官方说明](https://nextjs.org/docs/app/getting-started/route-handlers) |
| 原书阅读/提取 | PDF.js，翻页、缩放、文字选择/高亮与出处定位 | 官方示例支持页渲染，`getTextContent` 返回页文字；段落顺序和可靠锚点仍需自己处理。[示例](https://mozilla.github.io/pdf.js/examples/) · [页 API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html) |
| 图谱 | React Flow，章节分组和简单固定排序布局 | 自定义 React 节点适合产物徽标/出处入口；官方保存示例包含节点、边、视口。布局和活动层是应用逻辑。[自定义节点](https://reactflow.dev/learn/customization/custom-nodes) · [保存恢复](https://reactflow.dev/examples/interaction/save-and-restore) |
| 模型边界 | 服务端 OpenAI Responses API + Structured Outputs，运行时校验 | 可作为路由计划、概念关系和产物描述的结构化接口候选；不能保证语义正确，必须处理拒绝与不完整结果并核对出处。[官方结构化输出指南](https://developers.openai.com/api/docs/guides/structured-outputs) |
| 产物层 | 按四个 kind 分离适配器和展示组件 | 交互 UI、生成图片、概念图、来源查找均保留；各路服务及深度待决，详见下节 |
| 保存 | IndexedDB，浏览器原生 API | 支持结构化数据和文件/Blob；适合单机作品集，不承担云同步。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) |

默认先使用团队熟悉的简单 CSS；没有必要为十小时 MVP 新增完整设计系统、agent 框架、向量数据库、账户系统或云端任务队列。PDF 和图谱组件置于浏览器端，模型请求留在服务端；长书请求以分块形式推进，避免把整书任务依赖于一次长连接。

**模型选择暂不锁定 ID。** 实现前从实际账号可访问、支持所需结构化输出的模型中，用同一段真实书文评估有效引用率、输出可用率和总延迟，满足预算者优先。文档核实的是接口能力，不是某个账号的开通状态；没有宣称具体价格或固定上下文上限。图片生成已在产品范围内，但提供商/接口仍待核对；不能由文本 API 的存在推断图片可用性。来源查找的外部服务也不能在 D09 未定时擅自选择。截图不属于 MVP。

## 四路带来的实现要求

| 路线 | 十小时实现建议（未批准） | 需验证/决定 |
| --- | --- | --- |
| 交互 UI | LLM 实时生成窄主题 UI 描述、解释、参数和组件组合，由 React 与已验证图形/计算组件承载 | 示例市场模型、参数边界及方程依据；自由生成代码方案另评估隔离。不能把“可拖动曲线”当作经济模型已正确 |
| 生成图片 | 独立图片生成适配器，异步状态、预览和 Blob 保存 | 提供商、实际模型/权限、延迟、失败及持久存储；本轮未验证图片 API，不填虚构 ID/价格 |
| 概念图 | LLM 输出关系/图形描述，经校验后 SVG 或图组件渲染 | 关系依据、布局、是否允许编辑；与整书图谱是不同产物 |
| 来源查找 | 暂建议演示书内相关段落检索 | 书内/外部范围待 D09；若外部获选需增加搜索/读取/引用核验适配器，模型凭记忆列书目不算检索 |

路由采用可返回路线数组的契约；规则路由、LLM 路由或混合策略均待选。建议先用真实选文检查一条与多条路线的选择合理性，记录理由与延迟。组合请求需要独立进度、局部失败和可重复保存；图片较慢不应让已完成的图解消失。高亮后是否自动执行仍待 D05，不由栈决定。

以上是实现建议，不将已确认四路缩成 SVG-only。十小时需要限定各路广度而非删改产品意图；若某路未实现，必须在演示状态表中标为未实现/预生成。

## 何时换方案

| 替代 | 何时合理 | 对十小时的影响 |
| --- | --- | --- |
| Vite 前端 + 单独后端 | 团队已有成熟模板，或偏好独立服务 | 从零会多一套启动和请求配置；不是当前默认 |
| 直接复用 PDF.js 完整 viewer | 阅读器工具比图谱闭环更重要 | 需验证与应用选区、页码事件的集成；不要假设 iframe 内能直接使用应用状态 |
| 通用图可视化/3D 渲染方案 | D04 确认 3D，或算法图分析成为核心 | 重新评估文字、拾取、相机与产物面板；当前 React Flow 提案不覆盖 3D |
| 云数据库和对象存储 | 必须多人、登录、跨设备、公开长期部署 | 增加身份、上传和数据管理；应削减其他功能后再选 |
| 直接把整份 PDF 送给模型 | 图表保真优先，且接口/预算已验证 | 不自动解决原书跳转锚点；当前默认先提取可定位文字 |
| 自由生成 HTML/JS | D06 选择自由代码作为交互 UI 实现方式 | 需隔离运行和行为验证；使用已验证渲染器是另一实现候选，两者均服务于生成交互 UI 意图 |

这些替代是取舍条件，不是已验证兼容的备用栈。十小时结束前只维护一条实现路径。

## 必须做的小型验证

实现早期验证 PDF 选区/持久高亮、跨行跨页映射、五个出处，以及路由的单路/多路返回。随后分别预检交互 UI、真实图片输出、概念图和待确认范围的来源查找，不以一个文本请求成功代表四路接通。记录实际耗时和用量，不以宣传上下文长度或理论吞吐量推算整书时间。若预检失败，按执行计划降级并透明标注。
